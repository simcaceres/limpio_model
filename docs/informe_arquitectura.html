2.2. Respuestas _MVP (2).docx

Es el documento de respuestas del cliente. Se organiza en tres bloques:

Bloque 1 — Usuarios, perfiles y control de acceso

  • La creación y habilitación de usuarios la hace un administrador de RR.HH.
  • Solo acceden funcionarios con contrato a plazo fijo o indefinido de la Corporación/Área de Salud.
  • Perfiles oficiales del MVP: Funcionario, Jefatura, Administrativo, Recursos Humanos y Administrador del sistema.
  • Actor de apoyo: TI/Ciberseguridad (acceso excepcional, autorizado y trazable).
  • La matriz de acceso también menciona un Supervisor institucional (reportes e indicadores de su ámbito).
  • Cada perfil tiene acciones principales definidas (consultar, cargar, validar, aprobar/rechazar, registrar observaciones, etc.).

Bloque 2 — Documentos, validación y aprobación

  • Matriz de acceso documental por perfil: qué puede consultar cada uno y qué restricciones tiene.
  • Alcance por categoría documental: contratos y anexos, certificados laborales, solicitudes de permisos, licencias médicas, antecedentes personales sensibles, historial de modificaciones y reportes institucionales.
  • Reglas generales: el acceso se determina por perfil + dependencia + tipo de documento + función autorizada. El administrativo no tiene acceso transversal por defecto. El administrador del sistema no obtiene acceso automático al contenido sensible. Los cambios de cargo o dependencia gatillan revisión de permisos.

Bloque 3 — RF12: modificación de información y trazabilidad

  • Flujo de modificación con aprobación según el tipo de información.
  • Cambios simples (teléfono, correo): se aplican inmediatamente si el campo está habilitado, con trazabilidad.
  • Datos personales oficiales (nombre, RUT): requieren validación documental por RR.HH.
  • Contratos, anexos y documentos laborales: la nueva versión queda pendiente de revisión.
  • Documentos cargados por administrativo: no reemplazan al oficial hasta su validación.
  • Flujo: solicitud → evaluación (directo o con revisión) → aprobación (publica, actualiza y conserva versión anterior) o rechazo (mantiene versión vigente, registra motivo, notifica y permite reenviar).
  • Auditoría mínima: usuario responsable, fecha y hora, datos afectados, estado de la solicitud, resultado de la revisión y observaciones. El historial no puede ser alterado por usuarios ordinarios.
Idea clave del RF12: no basta con “editar”. Hay que distinguir entre edición directa y edición con aprobación, y mientras una modificación está pendiente, la información anterior sigue vigente. Eso exige estados, versiones y auditoría, que la app actual no tiene.

7. Arquitectura por capas: el mapa completo

La app sigue una separación inspirada en MVVM con repositorio. La dependencia va en un solo sentido: la UI conoce al ViewModel, el ViewModel conoce a los repositorios y los repositorios conocen las fuentes de datos. Ninguna capa “salta” a otra.

8. El flujo en orden: model, repository y demás

Esta es la parte que querías estudiar. Vamos de abajo hacia arriba, en el orden en que conviene entenderlo: primero el model (el vocabulario), después el repository (la puerta a los datos), después las fuentes de datos, luego el ViewModel (el coordinador) y al final la UI.

8.1. Model — el corazón y el vocabulario

El paquete model/ no conoce Android, ni Room, ni Compose. Son clases Kotlin puras. Por eso se pueden probar sin emulador. Aquí se define qué es un registro y qué reglas debe cumplir.

Ambito.kt — los cuatro mundos

enum class Ambito(val etiqueta: String, val descripcion: String) {
    NEURODESARROLLO("Neurodesarrollo", "Rutinas, tareas y autorregulacion"),
    DBT("Habilidades DBT", "Mindfulness, tolerancia, regulacion e interpersonal"),
    ANIMO("Estado de animo", "Check-in de emocion e intensidad"),
    ADICCIONES("Adicciones", "Impulsos, desencadenantes y acciones protectoras");

    companion object {
        fun desdeNombre(nombre: String?): Ambito =
            entries.firstOrNull { it.name == nombre } ?: NEURODESARROLLO
    }
}

Qué explica: un enum con etiqueta y descripción. desdeNombre convierte el texto que viene de la navegación o de Room en un valor seguro; si no coincide, cae en un valor por defecto. Eso evita crashs por datos viejos.

Catalogos.kt — las opciones dependen del ámbito

object Catalogos {
    fun tipos(ambito: Ambito): List<String> = when (ambito) {
        Ambito.NEURODESARROLLO -> listOf("Rutina", "Tarea", "Sobrecarga", "Autorregulacion")
        Ambito.DBT -> listOf("Mindfulness", "Tolerancia al malestar", ...)
        Ambito.ANIMO -> listOf("Feliz", "Tranquilo", "Neutro", "Ansioso", "Triste", "Irritable")
        Ambito.ADICCIONES -> listOf("Craving", "Impulso", "Recaida", "Objetivo cumplido")
    }

    fun rangoIntensidad(ambito: Ambito): IntRange =
        if (ambito == Ambito.ADICCIONES) 0..10 else 1..5
}

Qué explica: el catálogo es una función del ámbito. No hay listas duplicadas en la UI: la fuente de verdad está en el modelo. La intensidad cambia de rango según el ámbito (0–10 en adicciones, 1–5 en el resto).

RegistroUiState.kt — el estado del formulario

data class RegistroUiState(

Qué explica: un data class inmutable que representa todo lo que la pantalla necesita saber. errores es un mapa campo → mensaje. editandoId distingue crear de editar. No contiene lógica: solo datos.

RegistroValidator.kt — las reglas, sin UI

object RegistroValidator {
    fun validar(uiState: RegistroUiState): Map<String, String> = buildMap {
        if (uiState.tipo.isBlank()) put("tipo", "Selecciona un tipo")

        val rango = Catalogos.rangoIntensidad(uiState.ambito)
        if (uiState.intensidad !in rango)
            put("intensidad", "La intensidad debe estar entre ${rango.first} y ${rango.last}")

        if (uiState.ambito == Ambito.ADICCIONES && uiState.contexto.isBlank())
            put("contexto", "Indica el desencadenante")

        if (uiState.ambito == Ambito.DBT && uiState.estrategia.isBlank())
            put("estrategia", "Indica la habilidad practicada")

        if (uiState.ambito == Ambito.NEURODESARROLLO && uiState.estrategia.isBlank())
            put("estrategia", "Indica la estrategia utilizada")

        if (uiState.nota.length > 200)
            put("nota", "La nota no puede superar 200 caracteres")
    }
}

Qué explica: una función pura que recibe estado y devuelve errores. No muestra diálogos ni conoce Android. Por eso tiene 9 pruebas unitarias y es fácil de razonar.

            val delAmbito = registros.filter { it.ambito == ambito.name }
            ResumenAmbito(
                ambito = ambito,
                cantidad = delAmbito.size,
                promedioIntensidad = if (delAmbito.isEmpty()) 0.0
                    else delAmbito.sumOf { it.intensidad }.toDouble() / delAmbito.size,
                ultimaFecha = delAmbito.maxOfOrNull { it.fechaHora }
            )
        }
}

Qué explica: el resumen se calcula en el modelo, no en la pantalla. La UI solo dibuja el resultado. Esto permite probar los promedios sin emulador.

8.2. Repository — la puerta de los datos

El repositorio es una clase que esconde de dónde vienen los datos. El ViewModel no sabe si los datos están en Room, en memoria o en una API; solo llama al repositorio. Eso permite cambiar la fuente sin tocar la UI.

RegistroRepository.kt

class RegistroRepository(
    private val dao: RegistroDao,
    private val api: LemacApi = FakeLemacApi()
) {
    val registros: Flow<List<RegistroEntity>> = dao.observarTodos()

    fun observarPorAmbito(ambito: Ambito): Flow<List<RegistroEntity>> =
        dao.observarPorAmbito(ambito.name)

    suspend fun guardar(registro: RegistroEntity): Boolean =
        if (registro.id == 0) dao.insertar(registro) != -1L
        else dao.actualizar(registro) > 0

    suspend fun eliminar(registro: RegistroEntity) = dao.eliminar(registro)
    suspend fun obtener(id: Int) = dao.obtenerPorId(id)
    suspend fun obtenerTodos() = dao.obtenerTodos()
    suspend fun eliminarTodos() = dao.eliminarTodos()

    suspend fun sincronizar(): Int {
        val pendientes = dao.obtenerPendientes()
        if (pendientes.isEmpty()) return 0
        api.sincronizar(pendientes).getOrThrow()
        dao.marcarSincronizados(pendientes.map { it.id })
        return pendientes.size
    }

    suspend fun cargarDemo(alias: String): Boolean { /* inserta 4 registros si esta vacio */ }
}

Qué explica, método por método:

MétodoQué hace y por qué
registrosExpone un Flow del DAO. Cada cambio en la base emite una nueva lista; la UI se actualiza sola.
observarPorAmbitoFiltra por ámbito sin que el ViewModel escriba SQL.
guardarDecide insertar o actualizar según id. Devuelve Boolean para que el ViewModel sepa si funcionó.
eliminarBorra una fila.
obtener/obtenerTodosLecturas puntuales para editar o exportar.
sincronizarToma pendientes, llama a la API y los marca como sincronizados.
cargarDemoInserta datos de ejemplo solo si la tabla está vacía (evita duplicados).

8.3. Fuentes de datos — Room, SharedPreferences, API falsa, CSV y archivos

Room: RegistroDao.kt

@Dao
interface RegistroDao {
    @Query("SELECT * FROM registros ORDER BY fechaHora DESC, id DESC")
    fun observarTodos(): Flow<List<RegistroEntity>>

    @Query("SELECT * FROM registros WHERE ambito = :ambito ORDER BY fechaHora DESC")
    fun observarPorAmbito(ambito: String): Flow<List<RegistroEntity>>

    @Query("SELECT * FROM registros WHERE id = :id")
    suspend fun obtenerPorId(id: Int): RegistroEntity?

    @Insert suspend fun insertar(registro: RegistroEntity): Long
    @Update suspend fun actualizar(registro: RegistroEntity): Int
    @Delete suspend fun eliminar(registro: RegistroEntity)

    @Query("UPDATE registros SET sincronizado = 1 WHERE id IN (:ids)")
    suspend fun marcarSincronizados(ids: List<Int>)

    @Transaction
    suspend fun insertarDemoSiVacio(registros: List<RegistroEntity>): Boolean {
        if (contar() > 0) return false
        registros.forEach { insertar(it) }
        return true
    }
}

Qué explica: el DAO mezcla dos estilos. Las consultas que la UI observa devuelven Flow; las operaciones puntuales son suspend. @Transaction garantiza que “contar y luego insertar” sea atómico.

Room: LemacDatabase.kt

@Database(entities = [RegistroEntity::class], version = 1, exportSchema = false)
abstract class LemacDatabase : RoomDatabase() {
    abstract fun registroDao(): RegistroDao

    companion object {
        @Volatile private var INSTANCE: LemacDatabase? = null

        fun getDatabase(context: Context): LemacDatabase =
            INSTANCE ?: synchronized(this) {
                Room.databaseBuilder(context.applicationContext,
                    LemacDatabase::class.java, "lemac_datalab.db")
                    .fallbackToDestructiveMigration()
                    .build().also { INSTANCE = it }
            }
    }
}

Qué explica: el patrón singleton con @Volatile y synchronized evita crear dos bases. fallbackToDestructiveMigration borra y recrea si cambia el esquema: cómodo para un MVP, peligroso en producción.

Guardar: el método más importante

fun guardar() {
    val errores = RegistroValidator.validar(uiState)
    if (errores.isNotEmpty()) {
        uiState = uiState.copy(errores = errores)
        return
    }

    val formulario = uiState
    uiState = uiState.copy(cargando = true, guardadoExitoso = false, errores = emptyMap())

    viewModelScope.launch {
        val existente = formulario.editandoId?.let { id ->
            runCatching { registroRepository.obtener(id) }.getOrNull()
        }
        val registro = RegistroEntity(
            id = formulario.editandoId ?: 0,
            usuarioAlias = perfil.alias.ifBlank { "Usuario de prueba" },
            ambito = formulario.ambito.name,
            tipo = formulario.tipo.trim(),
            intensidad = formulario.intensidad,
            contexto = formulario.contexto.trim(),
            estrategia = formulario.estrategia.trim(),
            nota = formulario.nota.trim(),
            estadoObjetivo = formulario.estadoObjetivo.trim(),
            fechaHora = existente?.fechaHora ?: System.currentTimeMillis(),
            sincronizado = false
        )
        val guardado = registroRepository.guardar(registro)
        uiState = uiState.copy(
            cargando = false,
            guardadoExitoso = guardado,
            mensaje = if (guardado) "Registro guardado" else "No se pudo guardar"
        )
    }
}

Qué explica: valida primero, sin tocar la base. Si hay errores, no hace nada más. Si todo está bien, construye la entidad, llama al repositorio dentro de viewModelScope y actualiza el estado. La UI reacciona al nuevo estado.

9. Un registro paso a paso, de la pantalla a la base de datos

Este es el recorrido completo de “guardar un registro nuevo”. Sirve para explicar la arquitectura en una defensa sin memorizar código.

#PasoQué ocurre y en qué archivo
1El usuario toca una tarjeta de ámbitoHomeScreen llama onAmbito(ambito). AppNavigation navega a Rutas.registro(ambito).
2Se abre el formularioRegistroScreen recibe ambito e id = null. En LaunchedEffect llama viewModel.prepararFormulario(ambito, null).
3El usuario completaCada campo llama actualizarTipo, actualizarIntensidad, etc. Todos actualizan uiState con copy().
4Toca “Guardar”La pantalla llama viewModel.guardar().
5ValidaciónRegistroValidator.validar(uiState) devuelve un mapa de errores. Si hay errores, se muestran y el flujo termina.
6Construcción de la entidadEl ViewModel arma RegistroEntity con el alias del perfil, el ámbito, los campos recortados, fechaHora y sincronizado = false.
7RepositorioregistroRepository.guardar(registro) decide: si id == 0, dao.insertar; si no, dao.actualizar.
8RoomEl DAO ejecuta el SQL contra lemac_datalab.db. Room devuelve el id o la cantidad de filas afectadas.
9Nuevo estadoEl ViewModel actualiza uiState con guardadoExitoso = true y un mensaje.
10La lista se entera solaEl Flow de registros emite la nueva lista. resumen se recalcula. La UI se recompone.
11ConfirmaciónLaunchedEffect(guardadoExitoso) muestra el mensaje o vuelve atrás.
Para explicar en 20 segundos: “La pantalla no guarda nada. Le avisa al ViewModel. El ViewModel valida con el modelo, arma la entidad y le pide al repositorio que la guarde. El repositorio usa el DAO de Room. Cuando Room escribe, el Flow avisa y la lista se actualiza sola.”

Editar un registro

El flujo es casi el mismo, con dos diferencias: la navegación incluye ?id=5, prepararFormulario(ambito, 5) carga el registro y llena el estado; al guardar, id = 5 hace que el repositorio actualice en vez de insertar. La fechaHora original se conserva y sincronizado vuelve a false para indicar que hay cambios pendientes.

10. Otros flujos: sincronizar, exportar CSV y recordatorio

10.1. Sincronizar con la API simulada

fun sincronizar() {
    viewModelScope.launch {
        uiState = uiState.copy(cargando = true)
        runCatching { registroRepository.sincronizar() }
            .onSuccess { cantidad ->
                uiState = uiState.copy(cargando = false,
                    mensaje = if (cantidad > 0) "Sincronizados $cantidad registros"
                              else "No hay registros pendientes")
            }
            .onFailure { uiState = uiState.copy(cargando = false,
                mensaje = "No se pudo sincronizar") }
    }
}

Recorrido: ViewModel → repositorio → dao.obtenerPendientes() → api.sincronizar(pendientes) (espera 700 ms) → dao.marcarSincronizados(ids). No hay red real.

10.2. Exportar a CSV

  1. El usuario pulsa “Exportar datos (CSV)” en Ajustes o Resumen.
  2. BotonExportarCsv lanza ActivityResultContracts.CreateDocument("text/csv") (SAF).
  3. El sistema abre el selector de documentos; el usuario elige dónde guardar.
  4. viewModel.exportarCsv(uri) lee todos los registros con registroRepository.obtenerTodos().
  5. RegistroCsvExporter.generar(lista) produce el texto.
  6. contentResolver.openOutputStream(uri) escribe el archivo en Dispatchers.IO.
  7. Se muestra “Datos exportados (N registros)”.

No se pide permiso de almacenamiento porque SAF otorga acceso temporal al archivo elegido.

10.3. Recordatorio diario

  1. El usuario activa el recordatorio en Ajustes.
  2. PerfilRepository.guardarRecordatorio(true) lo persiste.
  3. RecordatorioScheduler.programar(context) crea un PeriodicWorkRequest de 1 día con retraso inicial hasta las 20:00.
  4. WorkManager ejecuta RecordatorioWorker.doWork().
  5. NotificacionHelper.mostrar(context) publica una notificación genérica si hay permiso POST_NOTIFICATIONS.

Limitación: la notificación no distingue eventos (aprobación, rechazo, vencimiento). Para el sistema documental habría que crear notificaciones por evento.

10.4. Foto de perfil

SelectorFotoPerfil usa TakePicturePreview, que no requiere permiso CAMERA. El bitmap se pasa a viewModel.actualizarFoto(bitmap), que guarda en Dispatchers.IO con FotoStorage.guardar y persiste la ruta en SharedPreferences.

11.3. Limitaciones reales del MVP

  • No hay backend real ni autenticación.
  • La base Room no está cifrada.
  • fallbackToDestructiveMigration puede borrar datos al cambiar el esquema.
  • El CSV es texto plano e incluye alias y notas.
  • No es un instrumento de diagnóstico ni reemplaza atención profesional.
  • No hay cuentas ni separación paciente/profesional (para Carta de Ánimo).
  • No hay documentos, roles, permisos ni auditoría (para el sistema documental).
Para producción harían falta: autenticación, autorización por roles, cifrado en reposo y en tránsito, consentimiento informado, auditoría, gestión de sesiones, y cumplimiento normativo de datos de salud. Nada de eso está en el MVP.

12. Cómo crear tu propio proyecto con esta misma idea

Tu objetivo es “crear uno mismo, pero diferente a mi manera”. La buena noticia es que la forma de organizar el código se repite. Lo que cambia es el dominio. Esta es la receta, en el mismo orden que estudiamos.

12.1. Receta general (7 pasos)

#PasoQué haces

2Define los contratosInterfaces de DAO, API y repositorios. Piensa en qué operaciones necesita la app, no en cómo se implementan.
3Implementa las fuentesRoom (Entity/DAO/Database), API real o fake, archivos. Aquí sí usas Android.
4Implementa el repositorioUne las fuentes y aplica reglas de negocio. El ViewModel solo ve el repositorio.

7Conecta y pruebaApplication como contenedor, Factory, navegación, pruebas unitarias de la lógica pura.
