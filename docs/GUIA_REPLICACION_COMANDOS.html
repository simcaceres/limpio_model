0. Guía de traspaso para principiantes (empieza aquí)

Esta parte está escrita para una persona sin conocimientos previos de Android, Kotlin ni de este repositorio: no supone que sabes programar y explica primero el vocabulario, después el mapa del proyecto y por último los comandos. Las secciones 1 a 15 que siguen son la referencia técnica detallada y siguen siendo válidas; aquí solo se anticipa lo imprescindible para que puedas entenderlas y continuar el trabajo.

Regla de lectura Primero identifica la capa, después el archivo y después la responsabilidad. No hace falta memorizar cada línea, pero sí poder explicar qué hace cada pieza y por qué está separada de las demás.

0.3 Cómo se recorre una pantalla (paso a paso, de punta a punta)

Ejemplo real: abrir un ámbito en Bienestar y guardar un registro. Así viaja un dato por las capas:

  1. UI (Compose) — ui/screens/HomeScreen.kt: el usuario toca una tarjeta de ámbito. La pantalla llama a la navegación (Rutas.registro(ambito) en navigation/AppNavigation.kt).
  2. Navegación — AppNavigation.kt resuelve la ruta registro/{ambito} y muestra ui/screens/RegistroScreen.kt.
  3. UI → ViewModel — RegistroScreen muestra campos y, al pulsar «Guardar», llama a viewmodel/RegistroViewModel.guardar().
  4. ViewModel — valida con model/RegistroValidator.kt (reglas puras, sin Android). Si hay errores actualiza RegistroUiState y la UI los muestra; si está bien, crea una entidad.
  5. ViewModel → Repository — llama a data/repository/RegistroRepository.guardar(...) (no habla directo con la base).
  6. Repository → DAO/Room — decide insertar o actualizar y usa data/local/RegistroDao.kt sobre RegistroEntity.kt.
  7. Room — escribe en lemac_datalab.db (configurada en data/local/LemacDatabase.kt) y expone los datos como Flow.
  8. Vuelta a la UI — el Flow emite la lista actualizada, el ViewModel la expone como StateFlow y Compose se recompone: Historial, Resumen y Home muestran el dato nuevo automáticamente.
Otro recorrido que conviene conocer En gestión documental, la pantalla «Documentos en línea» sigue la cadena Compose → DocumentosRemotosViewModel (StateFlow) → Repositorio → ApiService (@GET) → Retrofit → OkHttp → API mock y muestra tres estados: Cargando, Datos y Error (con botón Reintentar).

0.4 Arquitectura por capas y explicación de cada componente (rutas reales)

El proyecto sigue una separación inspirada en MVVM con un repositorio por fuente de datos. La dependencia va en un solo sentido: la interfaz conoce al ViewModel, el ViewModel a los repositorios y los repositorios a las fuentes. 0.5 Flujo de trabajo SDD con Lemoria (los 12 pasos y sus comandos)

SDD (Specification/Software Design Driven Development) significa desarrollo guiado por especificación y diseño. Lemoria es la CLI que guarda en PostgreSQL la fuente de verdad del proyecto: PRD, tareas, decisiones, commits, conversaciones y bóveda. La bóveda de Obsidian es solo una representación editable; PostgreSQL manda.

Lemac DataLab + Gestion Documental es una aplicacion Android unica que integra dos productos academicos en un solo APK. 4.3 Principios de diseno

  • Separacion de responsabilidades: la UI no conoce Room; el ViewModel no conoce Android Context salvo en la Factory.
  • Fuente de verdad unica: Room es la verdad local. La sincronizacion simulada no reemplaza la base.
  • Estado inmutable: cada pantalla observa un UiState y reacciona a cambios, sin mutar estado compartido a mano.
  • Inyeccion manual: no hay Hilt/Koin. La Application construye las dependencias y las Factory las pasan a los ViewModels.
  • Offline-first: todo funciona sin red; no se declara permiso de INTERNET.
  • Testabilidad: logica pura en model/ y dobles de prueba para repositorios y ViewModels.

6.4 Componentes transversales

Foto de perfil sin permiso CAMERA

SelectorFotoPerfil usa un contrato propio TomarFotoConUri:

  1. Crea un archivo temporal en cacheDir/fotos/captura_*.jpg.
  2. Lo expone con FileProvider (${applicationId}.fileprovider).
  3. Lanza ACTION_IMAGE_CAPTURE con EXTRA_OUTPUT, ClipData y flags de lectura/escritura.
  4. FotoStorage decodifica con inJustDecodeBounds + inSampleSize (lado maximo 1024 px) y aplica la orientacion EXIF (8 variantes).
  5. Guarda el resultado como PNG atomico en filesDir/perfil.png y limpia temporales de mas de 24 h.

El manifest solo declara <uses-feature android:name="android.hardware.camera" android:required="false" />. No hay uses-permission CAMERA: el intent de camara no lo necesita y se usa runCatching para el caso de camara no disponible.

Exportacion CSV local

Se usa Storage Access Framework: ActivityResultContracts.CreateDocument("text/csv"). El ViewModel recibe la Uri y ExportadorArchivo escribe con contentResolver.openOutputStream(uri) en Dispatchers.IO. No se pide permiso de almacenamiento, no se usa FileProvider para exportar y no se sube nada a la nube.

Formato del archivo: BOM UTF-8, cabecera fija, campos escapados segun RFC 4180, saltos CRLF y neutralizacion de formulas (si un campo empieza con =, +, - o @, se prefija con apostrofo). Nombre: lemac_datalab_yyyyMMdd_HHmmss.csv.

Recordatorios y notificaciones

RecordatorioScheduler programa RecordatorioWorker con WorkManager. NotificacionHelper crea el canal de notificaciones (Android 13+ exige POST_NOTIFICATIONS) y publica recordatorios discretos. Cada modulo tiene su propio canal para no mezclar avisos de bienestar con avisos documentales.

Backup selectivo

backup_rules.xml (API <= 30) y data_extraction_rules.xml (API 31+, con bloques identicos de cloud-backup y device-transfer) usan una lista de inclusion: domain="database" y domain="sharedpref" (acotado a perfil_lemac.xml). Excluyen explicitamente gestion_documental.db, sus -wal/-shm/-journal, files/documentos/ y file/perfil.png. La cache la excluye el sistema, no hace falta una regla.

8. Flujo de datos de extremo a extremo

Entender estos seis recorridos es lo que permite defender el proyecto y replicarlo sin copiar a ciegas. En todos, la UI emite eventos, el ViewModel decide y el repositorio persiste.

8.1 Crear un registro de bienestar

[Usuario] completa RegistroScreen
   -> onClick "Guardar"
   -> RegistroViewModel.guardar(datos)
       -> RegistroValidator.valida(datos)        // si hay errores, actualiza uiState.errores y termina
       -> clock()                                // hora actual inyectada
       -> RegistroRepository.insertar(entidad)   // id == 0 -> INSERT
           -> RegistroDao.insertar()
               -> Room / SQLite (lemac_datalab.db)
       -> FakeLemacApi.sincronizar()             // simulada, sin red
       -> actualiza uiState (lista, mensaje de exito)
   -> Compose recompone y muestra el registro en Historial/Resumen

8.2 Editar un registro

Al editar se conserva la fechaHora original y se fuerza sincronizado = false. Esto evita que el registro salte al tope del historial y garantiza que el cambio se reenvie en la siguiente sincronizacion. Si el registro ya no existe, se informa un mensaje claro y no se hace un UPDATE silencioso.

existente == null  -> mensaje "El registro ya no existe" (sin escritura)
existente != null  -> copia(fechaHora = existente.fechaHora, sincronizado = false)
                   -> RegistroRepository.actualizar()  -> UPDATE
                   -> uiState.registros se recalcula

class RegistroRepository(
    private val dao: RegistroDao,
    private val api: LemacApi
) {
    fun observarTodos(): Flow<List<RegistroEntity>> = dao.observarTodos()

    suspend fun guardar(registro: RegistroEntity): Result<Unit> = runCatching {
        if (registro.id == 0) {
            dao.insertar(registro)
        } else {
            val existente = dao.buscarPorId(registro.id)
                ?: error("El registro ya no existe")
            dao.actualizar(
                registro.copy(
                    fechaHora = existente.fechaHora,
                    sincronizado = false
                )
            )
            api.sincronizar(registro)
        }
    }

    suspend fun eliminar(registro: RegistroEntity) = dao.eliminar(registro)
}

class RegistroViewModel(
    private val repository: RegistroRepository,
    private val clock: () -> Long = System::currentTimeMillis
) : ViewModel() {

    private val _uiState = MutableStateFlow(RegistroUiState())
    val uiState: StateFlow<RegistroUiState> = _uiState.asStateFlow()

    init {
        viewModelScope.launch {
            repository.observarTodos().collect { lista ->
                _uiState.update { it.copy(registros = lista) }
            }
        }
    }

    fun guardar(datos: RegistroEntity) {
        val errores = RegistroValidator.validar(datos)
        if (errores.isNotEmpty()) {
            _uiState.update { it.copy(errores = errores) }
            return
        }
        viewModelScope.launch {
            _uiState.update { it.copy(cargando = true, errores = emptyMap()) }
            repository.guardar(datos.copy(fechaHora = clock()))
                .onSuccess { _uiState.update { s -> s.copy(cargando = false, mensaje = "Guardado") } }
                .onFailure { e -> _uiState.update { s -> s.copy(cargando = false, mensaje = e.message) } }
        }
    }
}

object RegistroCsvExporter {
    private const val BOM = "\uFEFF"
    private const val CRLF = "\r\n"

    fun generar(registros: List<RegistroEntity>): String = buildString {
        append(BOM)
        append("fecha,ambito,tipo,intensidad,contexto,estrategia,nota").append(CRLF)
        registros.forEach { r ->
            append(listOf(
                r.fechaHora.toString(),
                r.ambito,
                r.tipo,
                r.intensidad.toString(),
                escapar(r.contexto),
                escapar(r.estrategia),
                escapar(r.nota)
            ).joinToString(",")).append(CRLF)
        }
    }

    private fun escapar(campo: String): String {
        val neutralizado = if (campo.startsWith("=") || campo.startsWith("+") ||
            campo.startsWith("-") || campo.startsWith("@")) "'$campo" else campo
        return "\"" + neutralizado.replace("\"", "\"\"") + "\""
    }
}

Orquestador

Actua como orquestador SDD. Antes de empezar ejecuta `lemoria flow status <PRD_ID>`.

implementation-agent, frontend-agent, db-agent, testing-agent, review-agent,
documentation-agent y github-agent. Pasa siempre PROJECT_ID, PRD_ID, TASK_ID y CONV_ID.

Implementacion backend

Implementa la tarea <TASK_ID> del PRD <PRD_ID> en el proyecto <PROJECT_ID>.
Lee el PRD y las decisiones relacionadas. Respeta la arquitectura MVVM + Repository + Room.
No modifiques archivos fuera del alcance. Al terminar, reporta archivos tocados,
comandos ejecutados y resultado de build/tests.

Pruebas

Escribe y ejecuta pruebas para <TASK_ID>. Cubre logica pura y casos borde.
Usa JUnit 4 y kotlinx-coroutines-test. No uses Robolectric salvo necesidad justificada.
Ejecuta ./gradlew :app:testDebugUnitTest y reporta pass/fail con el conteo exacto.

Revision

Revisa la implementacion de <TASK_ID> contra el PRD <PRD_ID>. Busca bugs, deuda tecnica,
problemas de seguridad, permisos innecesarios y desalineacion con el PRD. Da un veredicto:
APROBADO, APROBADO CON OBSERVACIONES o CAMBIOS REQUERIDOS, con archivo:linea.

Documentacion

Actualiza README y docs para <TASK_ID>. Manten el estilo y las versiones reales.
No inventes funcionalidad. Al terminar, sincroniza el vault con
`lemoria vault sync <PROJECT_ID>` y reporta que archivos cambiaron.
